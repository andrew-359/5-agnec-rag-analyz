# Первая идея архитектуры

Черновик для команды. Собираем один путь от PDF до инженерного вывода. Общий объём работ описан в [плане реализации](../plan.md).

## Первый срез

Начинаем с цепочки `PDF → Python CLI → сохранённый прогон → CSV и просмотрщик`. Python читает таблицу, связывает числа с условиями эксперимента и сохраняет результаты метрик, фрагменты источника и замечания. Для каждого числа сохраняем страницу и таблицу, а при наличии координат — область ячейки.

Каждый прогон сохраняем в отдельный `run.json` с хешем исходного PDF и версией обработчика. Повторный запуск пишет новый файл. Из одного сохранённого прогона формируем CSV и показываем строки в просмотрщике. Так можно сверять результаты с эталоном и видеть, как меняются значения, их привязка и покрытие после изменения обработчика. На этом этапе достаточно файлов.

## Веб-загрузка и общая библиотека

- **React** обращается к Hono. Интерфейс показывает статус обработки, каталог и сравнение. Клик по результату открывает нужную страницу PDF и подсвечивает фрагмент источника, если есть координаты.
- **Hono** принимает PDF, сохраняет файл и создаёт задание. Через него интерфейс получает статус, опубликованные результаты с фильтрами и данные для открытия фрагмента источника.
- **Python-воркер** забирает задания и запускает тот же обработчик, что и CLI. Он сохраняет результаты и замечания, а готовую версию публикует целиком. Для первого релиза предполагаем один фоновый процесс. Отдельный HTTP API обработчика пригодится, если появится сетевой потребитель.
- **Сравнение** опирается на общие предметные правила в Python. Сопоставимость зависит от задачи, датасета, определения метрики и протокола оценки. Разницу считаем для сопоставимых результатов.

Для одного хоста и одного воркера предлагаем SQLite. В ней храним задания и их статусы, публикации и версии результатов для каталога. Исходные PDF и промежуточные файлы остаются в файловом хранилище. Postgres рассматриваем, если Hono и воркер будут на разных хостах или понадобится несколько воркеров с общей очередью.

### Очередь парсинга после первого релиза

Идея для обсуждения после того, как заработает весь путь от загрузки PDF до публикации в каталоге. К выбору очереди вернёмся, если одного воркера перестанет хватать по времени ожидания или обработчики понадобится масштабировать отдельно от Hono.

- **Postgres** — первый вариант для нескольких воркеров с общей таблицей заданий. Воркер атомарно забирает доступное задание через `FOR UPDATE SKIP LOCKED`, фиксирует срок владения и выполняет OCR вне транзакции. Если срок истёк, задание можно взять снова. Публиковать результат вправе текущий владелец задания.
- **RabbitMQ** — кандидат, если понадобится отдельный брокер для раздачи заданий. В сообщении передаём `job_id`, статус и результат остаются в БД. Создание задания и запись в `outbox` делаем в одной транзакции. Отправитель отмечает запись как отправленную после подтверждения брокера, воркер подтверждает обработку после сохранения результата. Для временных сбоев задаём задержку и предел повторов, после исчерпания попыток сохраняем причину ошибки для разбора.
- **Kafka** имеет смысл, если появится потребность хранить историю событий и независимо перечитывать её несколькими потребителями. Например, индексация, аудит и аналитика могут читать `DocumentParsed` каждый со своей позиции.

С любым вариантом проверяем два сбоя. Если воркер упал посреди OCR, задание снова становится доступным, а незавершённая версия остаётся скрытой. Если воркер упал после публикации, но до подтверждения обработки, повтор того же `job_id` возвращает сохранённый результат без второй публикации. Намеренный перепарсинг создаёт новое задание и может опубликовать новую версию.

## Первый сценарий демо

Берём Table 1 статьи D001, извлекаем через CLI и сверяем с эталоном 18 результатов ThreadRAG. Проверяем, что CSV и просмотрщик показывают те же результаты, а клик открывает страницу исходного PDF. Для демо сравнения затем можно взять RA-CoT и ThreadRAG на HotpotQA из той же таблицы. [Приёмка MVP](../plan.md#очерёдность-работы)

## Пробный запуск через MCP

Веб показывает сравнение и открывает ячейки в PDF. Объяснение сначала проверяем в чате. MCP-сервер даёт агенту один инструмент `get_comparison`: по двум ID он получает от того же бэкенда значения, условия, результат проверки сопоставимости и ссылки на источники.

Проверяем два случая. Для сопоставимых строк агент объясняет, какой инженерный вывод позволяют сделать данные, и ссылается на таблицу. Для строк с разными условиями он объясняет, почему по ним нельзя выбрать победителя. После этого тот же сценарий можно подключить к кнопке «Объяснить сравнение» в вебе.
