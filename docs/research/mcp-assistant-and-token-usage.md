# MCP, помощник оператора и учёт токенов в RAG

21 ноября 2026. Исследование по текущей рабочей копии RAG, исходникам Abstraction и официальной документации. Ниже предложены границы и приёмка пилота. Совместимость библиотек с RAG, ответы модели и расход на реальных вызовах предстоит проверить.

## Что согласовали для первой версии

- Начинаем с кнопки «Объяснить замечание» и одного инструмента `get_review_case`. Встроенный помощник на Vercel AI SDK и внешний MCP используют одну операцию. На D009 проверяем два исхода: подтверждённый генератор PRO-STEP и открытый генератор FLARE.
- Сначала подключаем локальный MCP к Codex через `stdio` и используем сохранённый прогон D009. Модели передаём выбранное замечание и короткие текстовые цитаты. Оригинальную ячейку оператор открывает в PDF по ссылке.
- Помощник предлагает значение со ссылкой на источник. Оператор кнопкой «Подставить» переносит его в черновик формы. Сохранение правки и публикацию обсуждаем отдельно.
- В вебе показываем токены за ответ и за чат. Сохраняем полученный от бэкенда usage один раз на ID ответа. Если часть расхода неизвестна, показываем известную сумму с этой пометкой. Для внешнего MCP ведём журнал вызовов инструментов. Детальный учёт по попыткам и расчёт стоимости остаются вариантами развития.

## Как это ложится на RAG

Основной путь от PDF до публикации и сравнения работает без LLM. Стратегии чтения и повторы принадлежат пайплайну, чья спецификация уже задаёт историю попыток, сохранение расхождений и автоматическую публикацию подтверждённой части. Помощник включается действием оператора возле замечания или сравнения. Он читает ту же сохранённую версию, объясняет основания и может предложить заполнение отдельного поля. Подтверждение и применение ручной правки потребуют отдельного контракта: спецификация привязки условий оставляет их за рамками. [Пайплайн](../../.scratch/extraction-pipeline/spec.md) · [Привязка условий](../../.scratch/table-context-binding/spec.md) · [Роль модели](../plan.md#роль-модели) · [Замысел кнопки помощника](../TO_THINK.md)

Фоновую LLM-попытку имеет смысл исследовать отдельно, если у нескольких статей числа читаются верно, а связь с условиями систематически теряется. Первый каскад по действующей спецификации использует две стратегии чтения таблицы. В отдельном эксперименте с LLM план заранее определяет входы, бюджет и причину запуска. Выход — утверждение об условии с областью действия и ссылкой на сохранённый фрагмент. Применимость проверяют предметные правила. Неоднозначность остаётся замечанием. Для проблем с текстом и сеткой скана, как в D021, сначала проверяется чтение той же области другим OCR на эталонных ячейках. [Контроль качества и роль модели](../plan.md#роль-модели) · [Прогон D021](table-parsing-pilots.md#запуск-d021-через-cli)

## Контракты для MCP и веба

Операции приложения читают сохранённые прогоны, проверяют доступ и возвращают типизированные данные. Hono может вызвать их напрямую из маршрута AI SDK, а внешний MCP-сервер может дать к тем же операциям протокольный доступ. Первыми достаточно двух независимых читающих контрактов, каждый нужен своему сценарию.

| Tool | Вход и результат |
| --- | --- |
| `get_comparison` | Два адреса опубликованных записей. Возвращает метрики, сравниваемые условия, рассчитанные разницы, вердикт с причинами и источники по полям. Имя совпадает с архитектурой первого среза. Серверный контракт сравнения остаётся владельцем расчёта и вердикта. |
| `get_review_case` | Адрес одного замечания или выбранного поля в сохранённом прогоне. Возвращает исходное число и ячейку, известные условия, открытое поле и причину, варианты и короткие проверяемые фрагменты, включая их область действия, страницы и ссылки. |

Адрес включает неизменяемую версию прогона или артефакта и ID внутри неё. Существующий JSON и веб-схему чтения стоит сверить вместе перед фиксацией контракта: адрес, нужный инструменту, должен явно входить в публичную схему. Для ещё не покрытого случая можно добавить узкий `get_source_excerpt` по ID фрагмента из уже доступного прогона. Первому пилоту достаточно вернуть небольшие фрагменты одним ответом. Доступ проверяется на каждом обращении по контексту приложения. Входы принимают предметные ID и ограниченные наборы полей. Каталоги, пути, произвольные URL и команды остаются вне схем. [Сравнение](../../.scratch/result-comparison/spec.md) · [Первый MCP-срез](../architecture/first-slice.md#пробный-запуск-через-mcp) · [Веб-схема прогона](../../web/src/shared/saved-run.ts) · [Формирование результата прогона](../../rag_mvp/run.py)

Для внешнего агента достаточно официального TypeScript SDK с `McpServer.registerTool`, входной и выходной схемой и структурированным результатом. Локальный эксперимент можно провести через `stdio`. Для отдельного сетевого клиента подходит Streamable HTTP с проверкой `Origin`, HTTPS и проверкой токена, выданного этому ресурсу. Права на PDF и версии прогонов проверяются дополнительно внутри handler. У SDK есть две линии: v1 `@modelcontextprotocol/sdk` поддерживает спецификацию до 2025-11-25, v2 `@modelcontextprotocol/server` реализует 2026-07-28, где у транспорта больше нет протокольных сессий и GET-потока. Перед выбором зафиксировать версию и провести smoke `tools/list` → `tools/call` именно с целевым хостом. Сессия оператора живёт в RAG. [MCP TypeScript SDK v1](https://ts.sdk.modelcontextprotocol.io/) · [SDK v2](https://ts.sdk.modelcontextprotocol.io/v2/) · [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) · [Авторизация MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

Для собственного веба вызов обработчика внутри приложения убирает сетевой переход. `createMCPClient` из `@ai-sdk/mcp` полезен при потреблении отдельного MCP-сервера. Он преобразует инструменты в AI SDK tools. При таком подключении сервер приложения выбирает разрешённые инструменты и закрывает клиент по окончании, ошибке или отмене. Набор поддерживаемых транспортных возможностей зависит от версии клиента. В проверенной локальной сборке Abstraction `@ai-sdk/mcp@2.0.84` заявлены протоколы 2026-07-28 и 2025-11-25. Это наблюдение по коду сборки. [AI SDK MCP Tools](https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools) · [`createMCPClient`](https://ai-sdk.dev/docs/reference/ai-sdk-core/create-mcp-client)

## Объяснение и черновик в UI

Для React и Hono подходят `useChat` из `@ai-sdk/react`, серверный `streamText` и `toUIMessageStreamResponse`. Можно начать с панели рядом с выбранным замечанием. Она показывает прочитанное значение, причину открытого поля, ссылки на ячейку и цитату и, при наличии прямого основания, предварительно заполненное поле. Модель возвращает небольшой структурированный ответ: `proposed` с полем, значением, ID источников и пояснением либо `needs_review` с причиной и доступными основаниями. Сервер проверяет схему, принадлежность ссылок переданному случаю, значение поля и актуальность версии. PDF-фрагменты передаются как данные. Текст статьи не может менять инструкции, права или список инструментов. При использовании внешнего провайдера допустимый объём и виды данных определяет проект. Для пилота достаточно очищенных коротких фрагментов или синтетического эквивалента. [Веб RAG](../../web/README.md) · [`streamText`](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text) · [`useChat`](https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat)

Черновик сначала можно держать в форме. Сохранение подтверждённой правки, если его поручат, проходит через явное действие оператора и проверки прав, версии и основания в приложении. AI SDK также поддерживает подтверждение выполнения tool через `needsApproval` и `addToolApprovalResponse`. Этот протокол завершает первый запрос и продолжает обработку новым вызовом, что влияет на учёт. Пилоту достаточно читающих инструментов и черновика в форме. Для численных выводов ссылки и вердикт приходят из результата tool. Текст ответа модели поясняет этот результат, а переходы в PDF строит UI по проверенным адресам. [Tool Calling](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling) · [Chatbot Tool Usage](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)

Из Abstraction (проверенная рабочая копия, HEAD `0bd0b0a`) можно взять `createAssistant`, панель и типизированные инструменты. Серверный helper валидирует сообщения и передаёт параметры `generation` в `streamText`. В исходнике по умолчанию `maxRetries: 0` и до четырёх шагов на один серверный запрос. Историей сообщений, правами, побочными эффектами и общим лимитом операции владеет приложение. Для пилота полезны схема входа и проверка выхода из tool-kit. Схема валидации сообщений сама по себе не подтверждает, что история принадлежит оператору или что присланный клиентом результат tool настоящий. ## Токены на запрос и сессию

Единица учёта — фактическая попытка обращения к провайдеру. В одной операции оператора (`operationId`) может быть несколько HTTP-запросов AI SDK (`requestId`), в каждом несколько шагов, в шаге возможны повторные вызовы. `sessionId` объединяет операции одного чата, у фоновой работы вместо сессии есть контекст прогона и этапа. Для повторной доставки одного события используется прежний ID попытки, для нового обращения к модели создаётся новый. Повтор учитывается отдельно даже при одинаковом тексте. Ориентир по метрикам из Abstraction зафиксирован в `projects/houston/docs/hackathon-preparation.md`, раздел «Учёт токенов и Grafana». [Проектный контекст Houston](../context/houston.md) · [Жизненный цикл AI SDK](https://ai-sdk.dev/docs/ai-sdk-core/generating-text)

| Что хранить на сервере | Для чего |
| --- | --- |
| `callId`, `traceId`, `operationId`, `requestId`, номер шага и попытки, `sessionId` либо ID фоновой работы, время и вид операции | Связать событие до вызова с ответом, повтором или отменой. Один `callId` — одна запись с идемпотентным обновлением. |
| Запрошенный и фактический ID модели, провайдер, режим/тариф при наличии, отдельные provider request ID и response ID при наличии | Сверить маршрутизацию, цену и обращение к провайдеру. В OpenAI HTTP request ID доступен в `x-request-id`. |
| Исход выполнения, `usageStatus`, фактические `inputTokens`, `outputTokens`, `totalTokens`, детали кэша и reasoning при наличии | Суммировать подтверждённый расход и отдельно показать количество попыток с частичным или неизвестным расходом. Оценки при необходимости лежат отдельно. |

В локально проверенном AI SDK 7.0.153 `onStepEnd` даёт usage завершённого шага (`onStepFinish` — устаревшее имя). Для кэша и reasoning есть `inputTokenDetails.cacheReadTokens`, `inputTokenDetails.cacheWriteTokens` и `outputTokenDetails.reasoningTokens`. `streamText().usage` относится к последнему шагу, `totalUsage` суммирует шаги ответа. В исходнике этой версии агрегат складывает известные значения и может скрыть пропуск usage одного из шагов. Поэтому `totalUsage` подходит для сверки, а полнота считается по записям отдельных попыток. Для пилота отключить SDK-ретраи и регистрировать попытку до вызова. В AI SDK 7 есть `onLanguageModelCallStart` и `onLanguageModelCallEnd`, причём в исходнике `streamText` SDK использует общий `callId` и при повторе. Нужен свой ID каждой фактической попытки и обработка ошибки или отмены. Если продукт позднее включает ретраи, инструментировать границу обращения и проверить трассировку на тесте с повтором. Недоступные сведения о внутренних попытках шлюза отмечаются явно. При обрыве стрима сохраняются уже известные строки и отдельно отмечается незавершённая попытка. `messageMetadata` на finish подходит для отображения расхода ответа в UI, а запрос и сессию приложение сводит по серверному журналу. Чисто читающий MCP-вызов с внешней моделью оставляет отдельный след операции, поскольку usage модели внешнего хоста MCP tool не получает. [AI SDK `streamText`](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text) · [Колбэки и usage в AI SDK 7](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0) · [Отмена](https://ai-sdk.dev/docs/ai-sdk-core/error-handling) · [Message Metadata](https://ai-sdk.dev/docs/ai-sdk-ui/message-metadata) · [OpenAI API request IDs](https://developers.openai.com/api/reference/overview)

Нулевой расход означает подтверждённый ноль. Если в сессии есть 1250 известных токенов и один вызов без usage, интерфейс показывает обе величины. Отдельно можно ограничивать размер входных фрагментов, выход, число шагов, общее время и число обращений на операцию. Когда нужен лимит в деньгах, допуск следующего вызова опирается на консервативную оценку входа и резерв выхода, а резерв корректируется после получения usage. [OpenAI Cookbook: spending controller](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api)

В OpenAI Responses cached input входит в общий input, reasoning входит в общий output. При 1000 входных токенах, из них 300 кэшированных, и 250 выходных, из них 100 reasoning, общий расход — 1250 токенов. Без отдельной тарификации записи в кэш стоимость — 700 по обычному входному тарифу, 300 по кэшированному и 250 по выходному. Для профилей с платной записью в кэш её токены тоже выделяются из общего входа. Имена и детализация полей зависят от провайдера. По этой причине сохраняем модель, профиль расчёта, версию тарифов и валюту вместе с оценкой стоимости. Стоимость встроенных инструментов и режимов учитывается по тарифу отдельно, если она доступна. Сверка с агрегированным Costs API выполняется за период по провайдеру и проекту. [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) · [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning) · [Тарифы API](https://developers.openai.com/api/docs/pricing) · [Costs API](https://developers.openai.com/api/reference/typescript/resources/admin/subresources/organization#costs)

Для пилота достаточно небольшого серверного журнала с выборками по запросу и сессии. Для Grafana агрегируются токены, число попыток, длительность и число попыток без usage по виду операции, провайдеру и ограниченному набору моделей. Уникальные ID остаются в журнале, тексты и значения из статей в метрики не попадают. [Prometheus: naming and labels](https://prometheus.io/docs/practices/naming/)
