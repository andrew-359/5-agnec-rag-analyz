# Готовые решения для извлечения и сравнения результатов из научных PDF

Обновлено 20 ноября 2026 года. Продукты сверены по документации, публикациям разработчиков и открытому коду. Локальные результаты на D001 и D013 приведены в разделе о переиспользовании. PDF из корпуса в сервисы не загружались.

**Полную замену для кейса ВИНИТИ по открытым источникам не нашли.** Близкие аналоги уже существуют. SciLead автоматически строит лидерборды из научных PDF, Papers with Code даёт готовый каталог ML-результатов, а платформы извлечения умеют возвращать значения с привязкой к PDF. Основной объём своей разработки — проверяемая связь числа с условиями конкретного RAG-эксперимента, правила сравнения и пакет сдачи.

## Что должно закрыть готовое решение

После загрузки нового PDF система должна выделить отдельные измерения и сохранить для каждого численное значение, метрику, конфигурацию, датасет, задачу и протокол. Из поля результата можно открыть одно или несколько оснований в исходном PDF, вплоть до ячейки таблицы. Библиотека сравнивает записи только при совместимых условиях и выгружает пакет по формату кейса. Тесты различают пропуск, неверное число, неверную связь числа с экспериментом и ошибочный переход к источнику. В проекте базовый путь запланирован без LLM. [Устройство системы](../system.md) · [Первый срез](../architecture/first-slice.md) · [Спецификация переходов](../../.scratch/source-links/spec.md) · [Формат корпуса и выгрузка](../context/viniti.md)

В первом срезе CLI читает заданную страницу и таблицу через Docling, сохраняет JSON и CSV, а локальный просмотрщик показывает результаты и прямоугольник ячейки. Четыре предметных теста покрывают одинаковые числа в разных столбцах, частичное чтение mean/SD, неполную шапку и отсутствие протокола. ## Продуктовые аналоги для ML-бенчмарков

**Papers with Code от Hugging Face** уже даёт каталог статей и методов, многометрические лидерборды, поиск и REST API. При добавлении внешней статьи описано автоматическое обогащение, включая результаты оценивания. В модели публикации результата есть задача, датасет, модель, окружение запуска, описание методики, метрики и ссылка на источник. В модели основания при проверке чисел есть исходное значение, шкала, URL и текстовый указатель на таблицу. Переходы от отдельных полей к координатам ячейки, загрузка произвольного локального PDF через тот же путь и экспорт по формату ВИНИТИ требуют отдельной проверки. Код платформы под Apache-2.0 с инструкцией локального запуска. Проверенный модуль импорта принимает уже подготовленные записи с результатами. Такой импорт можно использовать как образец контракта для границы между извлечением и каталогом. [Импорт](https://github.com/huggingface/paperswithcode/blob/main/backend/database/evaluations_setup/paper_eval_import.py) [Репозиторий](https://github.com/huggingface/paperswithcode) · [Перезапуск платформы](https://huggingface.co/blog/nielsr/paperswithcode-launch) · [Модели API](https://github.com/huggingface/paperswithcode/blob/main/backend/models/evaluations.py) · [Хранение результатов](https://github.com/huggingface/paperswithcode/blob/main/backend/models/database/evaluations.py)

**CodeSOTA** показывает близкую логику сравнения для уже собранных результатов. API выбирает лучший результат только в рамках совпадающих бенчмарка, метрики, версии, протокола и области оценки. При недостатке протокольных данных ответ может быть `409`. Есть ссылка на источник значения и данные о покрытии. Это референс правил сравнения. В публичном контракте показан поиск по реестру результатов, а путь от нового PDF к отдельным основаниям полей не описан. [Контракт `/api/sota`](https://www.codesota.com/api-landing/sota) · [Стандарт данных](https://www.codesota.com/methodology)

## Решение по первому срезу

1. Использовать локальный Docling для D001/Table 1. Проверять 18 записей ThreadRAG по ключу «метод, генератор, датасет, метрика», исходному числу и месту на странице. Два одинаковых `.586` должны остаться двумя результатами. SciLead даёт контрольный подход для автоматического извлечения смысловых полей, если понадобится LLM. [Контрольные примеры и протокол](viniti-pdf-extraction.md#короткий-эксперимент-для-выбора-базы)
2. Повторить сценарий на D013/Table 2. У mean и SD одна ячейка-основание. Читаемое среднее сохраняется при нечитаемом SD, по SD сохраняется замечание. D014 проверять отдельно по указанному допуску, поскольку его массовые точки могут скрыть ошибки в общей оценке. [Контрольные примеры](viniti-pdf-extraction.md#два-контрольных-примера) · [План оценки](../plan.md#очерёдность-работы)
3. Своими оставить связи результата с экспериментом и его условиями, основания конкретных полей, проверку сопоставимости и преобразование в семь CSV ВИНИТИ. Разницу между двумя значениями рассчитывать после подтверждения сопоставимости. [Проектное устройство](../system.md) · [Формат и чекер](../context/viniti.md)

## Что переиспользовать в коде

### Docling и RapidOCR для локального чтения

**D001, Table 1.** Сверил исходный PDF сохранённого прогона по SHA-256 с файлом корпуса. Все 18 результатов ThreadRAG совпали с `dev_gold` по генератору, датасету, метрике и десятичному значению. У всех есть координаты ячеек. Существующий адаптер уже использует интервалы `TableCell` и переводит прямоугольники к верхнему левому углу через `to_top_left_origin()`. Для восстановления основания поля можно сохранять тот же прямоугольник у найденных заголовков, строки метода и подписи. `TableData.grid` разворачивает объединённую ячейку во все покрытые позиции. ## Проект интеграции OCR-координат в ReadTable

Скан читаем через Docling и встроенный RapidOCR. Выход табличной модели даёт область таблицы, предполагаемую сетку и подпись. OCR отдельно возвращает текстовые фрагменты с координатами. Если табличная модель склеила или сдвинула ячейки, из этих фрагментов можно восстановить связи чисел со строкой и шапкой. Обе ветки формируют `ReadTable` для существующего `collect_results()`. Это проект реализации. Числа для D013 ниже получены в отдельной локальной пробе. [Парсер](../../rag_mvp/strategies/parser.py) · [Предметный модуль](../../rag_mvp/core/domain.py) · [План первого среза](../architecture/first-slice.md)

### Точка подключения

1. В CLI остаётся обычный вызов извлечения с номером страницы и таблицы. Для цифровых страниц используем существующие `TableCell` с интервалами строк и столбцов, шапкой и `bbox`. Для первого прогона на скане достаточно явно выбирать режим OCR. Автоматический выбор можно добавить по отсутствию читаемого текстового слоя в целевой области, включая смешанные PDF с текстом снаружи и сканом внутри.
2. В режиме OCR конвертируем целевую страницу через `PdfPipelineOptions` с `generate_parsed_pages=True`. Держим `ConversionResult` до конца разбора. Из `result.document` берём `TableItem.prov`, подпись и предложенные ячейки, а из `result.pages[*].parsed_page.textline_cells` — сырые OCR-фрагменты. Обычный `document.export_to_dict()` в проверенном прогоне этих фрагментов по страницам не содержал.
3. Сначала проверяем, можно ли сопоставить сетку, шапку и распознанное содержимое. Несколько меток методов или несколько числовых пар внутри одной предполагаемой ячейки, дублирование одного фрагмента в соседних ячейках и выход за границы области указывают на проблему со структурой. В этом случае пробуем восстановление по координатам для конкретной таблицы. Одного наличия прямоугольника или правильного числа для этой проверки мало.
4. Геометрический разбор остаётся в PDF-адаптере. `ReadCell` получает логические индексы строки и столбца, прочитанный метод, упорядоченный путь по шапке, исходный текст и `box`. Текущий предметный модуль уже умеет разбирать путь D001 «генератор → датасет → метрика» и путь D013 «retrieval top-k → датасет» с генератором и метрикой из подписи. `collect_results()` продолжает отвечать за интерпретацию условий, разбор значений, единицы, вид статистики и замечания. [Сохранение OCR-фрагментов](https://github.com/docling-project/docling/blob/v2.151.1/docling/pipeline/standard_pdf_pipeline.py#L760-L775) · [Текущий адаптер](../../rag_mvp/strategies/parser.py) · [Правила модели](../../rag_mvp/core/domain.py)

### Восстановление строк и столбцов

1. Выбираем область таблицы по номеру, странице и подписи. Переводим прямоугольник из provenance и OCR-координаты в одну систему координат страницы. Отбираем фрагменты в области таблицы, а текст подписи и окружающего раздела передаём в `ReadTable` как контекст. Если на странице несколько кандидатов, принадлежность подписи таблице проверяем до интерпретации ячеек.
2. В верхней части таблицы выделяем уровни шапки. Для D013 центры нижних заголовков `NQ`, `TriviaQA` и `HotpotQA` дают опорные позиции по горизонтали. Область каждого верхнего заголовка `Top-k = …` связываем с подтверждённой группой нижних столбцов. Одинаковое имя датасета в трёх группах даёт три отдельных столбца.
3. В первом столбце упорядочиваем фрагменты методов по вертикали. В числовой части сопоставляем OCR-фрагменты колонкам по положению относительно шапки. При перекосе страницы учитываем наклон строк. В пределах каждой колонки используем положение фрагмента относительно полосы конкретной строки. Если расстояние до соседней строки или колонки почти такое же, сохраняем неоднозначную привязку. Точные допуски проверяем на корпусе и фиксируем с параметрами прогона.
4. Каждый числовой фрагмент может занять только одну логическую ячейку. Пропуск образует пустое место в найденной строке. При двух кандидатах на то же место сохраняем оба фрагмента для проверки. Привязка соседних значений должна переживать единичный пропуск без сдвига. В пробе использовали упорядочивание по Y и строгую проверку полноты каждого столбца. При переносе этого подхода нужна проверка геометрии даже при полном числе фрагментов, поскольку пропуск и лишний фрагмент могут компенсировать друг друга.
5. Заполняем `ReadCell` по подтверждённой строке и полному пути шапки. Числовую пару передаём исходной строкой, например `24.5 (.29)`. Среднее и выборочное SD разбирает предметный модуль. Если распознана только часть пары, геометрический разбор передаёт ей то же место, оставляя решение о сохранении читаемого значения предметному модулю. Число без однозначных условий сохраняем в замечании вместе с найденным фрагментом. [Контрольные таблицы](viniti-pdf-extraction.md#два-контрольных-примера) · [Понятия проекта](../../GLOSSARY.md)

| Генератор, метрика и условия | На D001 — соответствующий уровень шапки и фрагмент §4.1 при наличии. На D013 — подпись с моделью, Exact Match, процентной шкалой, sample SD и двумя запусками. |

В промежуточных данных сохраняем номер страницы, исходную геометрию и её систему координат. Для `ReadCell.box` используем текущий формат `(left, top, right, bottom)` в долях ширины и высоты от верхнего левого угла страницы. OCR-прямоугольник, полученный на вырезке, сначала переводим обратно в координаты PDF с учётом начала вырезки, масштаба рендера и поворота. Перед выдачей проверяем границы и ненулевую площадь. Для `OAS / HotpotQA / retrieval top-k = 5` из D013/Table 2 OCR дал прямоугольник примерно `(0.795531, 0.494520, 0.846672, 0.509139)` после нормализации. Он относится к тексту пары внутри ячейки.

Отдельно от `box` значения сохраняем адреса метода, уровней шапки, подписи и протокола, когда их удалось локализовать. В модели переходов эти адреса становятся фрагментами источника, связанными с версией PDF. У проверки числа и проверки его условий могут быть разные адреса. Для широкой области таблицы или страницы отдаём соответствующую точность, чтобы просмотрщик показывал размер реально найденного фрагмента. ### Нечитаемые фрагменты и повторный OCR

| Что произошло | Что сохраняем и проверяем |
| --- | --- |
| Табличная модель склеила строки, а OCR прочитал отдельные фрагменты | Используем координаты OCR для восстановления связей. Если геометрия по-прежнему неоднозначна, отдаём замечание с областью и распознанным текстом. |
| OCR потерял часть шапки, подписи или значения | Повторно распознаём небольшую область с параметрами рендера, сохранёнными в прогоне. При согласующемся чтении обновляем основание. Если варианты расходятся, сохраняем их для ручной проверки. |
| Ячейка читается, но потеряно условие группы | Храним текст и место числа. Результаты из этой группы требуют подтверждения условия перед сравнением. При `Topk-` порядок соседних групп сам по себе не определяет число. |
| Среднее читается, SD повреждено | При однозначных условиях сохраняем среднее. Для SD оставляем замечание с тем же местом в PDF. |
| Геометрия потеряна, текст или страница известны | Сохраняем наиболее точное доступное место. При восстановлении прямоугольника проверяем его на растре исходной страницы. |

На D013/Table 3 были видны восемь меток методов, девять заголовков датасетов и по восемь числовых пар в каждом столбце. OCR распознал среднюю метку `top-k` как `Topk-`. В сохранённом выводе Docling у этой таблицы также обрезано начало подписи с номером. Поэтому для сквозного прогона нужно подтвердить и номер таблицы по области подписи, и значение группы по области шапки. Проба выбрала известную область таблицы для диагностики и остановилась на проверке шапки. Это результат испытания переноса с теми же параметрами, а повторный OCR области пока предлагается как следующий эксперимент.

### Как повторить пробу и проверить перенос

**Условия прогона.** Docling `2.151.1`, Docling Core `2.108.0`, RapidOCR `3.10.0`, PyTorch CPU, четыре потока. На входе исходный скан `dev/D013.pdf` из комплекта. Вызов `DocumentConverter.convert(pdf, page_range=(6, 6))` берёт только страницу 6. Для проверки переноса используем `page_range=(8, 8)`. Параметры `PdfPipelineOptions` — `do_ocr=True`, `do_table_structure=True`, `generate_parsed_pages=True`, `ocr_options=RapidOcrOptions(backend="torch", lang=["en"], mode=OcrMode.FULL_PAGE, scale=3)`. Первая ветка использует `TableStructureOptions(mode=TableFormerMode.ACCURATE, do_cell_matching=True)`, сравнение с V2 — `TableStructureV2Options(do_cell_matching=True)`. Сохраняем исходный JSON через `result.document.export_to_dict()`, а разобранные страницы через `page.parsed_page.model_dump(mode="json")` для тех страниц, у которых `parsed_page` доступна. [Версии проекта](../../requirements.txt) · [Параметры Docling](https://github.com/docling-project/docling/blob/v2.151.1/docling/datamodel/pipeline_options.py) · [Комплект участника](../context/viniti.md)

**Правило одноразовой пробы.** Внутри области таблицы отбирали фрагменты по положению центра. Метки методов брали из первого столбца по границе ячейки заголовка `Method`. Нижние заголовки распознавали по трём известным именам датасетов, верхние — по явному `Top-k = число`. Строки с числовой парой «среднее (SD)» распределяли по ближайшему центру заголовка датасета по X. Для колонки выбирали ближайший центр верхнего заголовка, затем сопоставляли восемь пар восьми методам в порядке Y. Перед сопоставлением требовали три верхних заголовка, девять нижних, восемь методов и по восемь пар в каждой колонке. Это настройки контрольной таблицы. Перед применением к другим формам таблиц учитываем геометрию, пропуски и неоднозначность, описанные выше.

**Сверка.** Сначала сохраняем результат извлечения, затем соединяем `dev_gold/results.csv` с `configurations.csv` и `datasets.csv`. Для этой пробы сравниваем мультимножества `(метод, retrieval top-k, датасет, вид статистики, Decimal-значение)` отдельно для каждой страницы и таблицы. Для короткой подписи вида `Ours (OAS)` сопоставляем название метода с `OAS`. Каждая строка эталона засчитывается один раз. Пропуск, неверное число, неверная связь с условиями и неверная область подсветки отмечаются отдельно. Полная приёмка учитывает остальные поля и правила из плана оценки. ### Порядок реализации

1. Сохранить координаты шапки и строки метода в текущем пути D001. На одном примере проверить различие между переходом к числу и переходом к его условию.
2. Подключить режим скана в том же CLI и добавить восстановление таблицы из координат Docling/RapidOCR. Сохранять сырой OCR отдельно от интерпретированных результатов. Сверить D013/Table 2 и записать случай нечитаемой шапки на Table 3 в общий выход замечаний.
3. По примеру AxCell проверять значения и смысловые поля отдельно, а геометрию сверять по ячейке там, где есть разметка. Если на других статьях повторяются сбои структуры, сравнить второй парсер на тех же входах. У Unstructured для этого есть низкоуровневый выход с координатами и диапазонами ячеек.
