## Исправленный сбой маршрута

В опубликованном наборе несколько замечаний могут относиться к одному фрагменту. До исправления нажатие сохраняло только `evidenceId`: выбранное замечание теряло идентичность, справа показывались все замечания этого фрагмента, после reload/закрытия нельзя было восстановить нужную запись.

Воспроизведение через настоящий сборщик публикации, Hono и Chrome: два замечания к одной реальной ячейке D001 → нажать второе → ожидался `remarkId=I2`, получен `null`. Регрессия `remark-route.spec.ts` сначала упала на этом утверждении, после изменения прошла. URL теперь хранит `remarkId`, сервер проверяет его принадлежность выбранному фрагменту и запрещает одновременный выбор результата и замечания. Список замечаний остаётся открытым, выбранная запись обозначена, закрытие возвращает фокус на неё, включая прямое открытие и reload. Старые ссылки только на фрагмент сохраняют прежний смысл.

На **реальном полном выпуске D001** отдельный `published-review.spec.ts` прошёл путь туда и обратно для:

- `.422` основной оценки, Table 1, PDF 6;
- `.422` абляции, Table 2, PDF 7;
- текстового прироста `14.4%`, PDF 7;
- точки Figure 3(a), anchors=1, EM `0.528`, PDF 8;
- замечания с координатами источника.

Проверены reload, возврат фокуса, PDF.js и отсутствие ошибок JS. Скачанный через браузер ZIP побайтно совпал с ZIP именно этой версии в общем хранилище. Дополнительно прошли шесть регрессий исходных ссылок, включая старый прогон, неверные ID, 252-ю строку и общий источник mean/SD.

## Где теряются данные

1. **Обнаружение.** D013: ни одна таблица не попала в план; 21 страница отмечена для проверки. Известная Table 2/PDF 6 не дошла до чтения. Смешанный контроль: страница 7 отмечена предупреждением, Tables 2 и 3 отсутствуют в плане. Ноль кандидатов не означает отсутствие таблиц в PDF.

В D001 отдельная проба pdfplumber на том же фрагменте (`--crop 70 65 525 555`) дала 0 результатов и два замечания. Это диагностическая ручная проба, не автоматическая поддержка fallback. Указанный фрагмент — case study с последовательностью рассуждений; его числа не становятся метриками по одному наличию цифр.

4. **Экспорт.** В этой пачке подтверждённые D001-результаты не потерялись при выгрузке; нулевые P003/D013 не выданы за успешные полные публикации. Пакеты частичны, причины сохранены. Отдельная ошибка экспорта фиксируется как `publication_status=failed`, а не как отсутствие таблицы.

## Воспроизведение

С поднятыми Hono/RabbitMQ/воркером из корня репозитория:

```bash
python runs/full_pdf_batch.py --origin http://127.0.0.1:4330 --out runs/my-batch \
  docs/context/RAG_ВИНИТИ_участникам_2026-11-20/dev/D001.pdf \
  docs/context/RAG_ВИНИТИ_участникам_2026-11-20/dev/D013.pdf \
  docs/context/RAG_ВИНИТИ_участникам_2026-11-20/test/P003.pdf
```

Повтор с тем же `--out` продолжает сохранённые ID без повторной подачи PDF. `--refresh` пересобирает отчёт завершённых ID из сохранённых артефактов и их HTTP-источников, не запускает извлечение. Изменившийся PDF по прежнему пути отклоняется по SHA-256. Новое извлечение — новый `--out`. Timeout сохраняет чекпойнт и возвращает 2. Технический отказ запуска/публикации — 1. Пустая диагностированная публикация остаётся терминальным исходом, не доказательством полноты.

Чтение ячеек для отчёта идёт через исходный `table-grid.json`, а не сокращённый ответ `RunResponse` для интерфейса. Скачанный ZIP проверяется по `versionId` в manifest. В `batch.json` есть ссылки на карточки, длительности и итоги; в подкаталогах — полные JSON, исходные сетки и ZIP.

Браузерная приёмка полного выпуска:

```bash
RAG_PYTHON=/path/to/.venv/bin/python PLAYWRIGHT_CHANNEL=chrome \
RAG_REVIEW_PUBLICATIONS=/absolute/path/to/runs/priority-one/publications \
E2E_PORT=4338 pnpm --dir web test:e2e published-review.spec.ts
```

Использован установленный Playwright/Chrome. PDF.js показал реальные страницы, автоматическая проверка не заменялась снимком. RabbitMQ поднят локально; официальный digest образа `cd4f5c5b…` получен через зеркало после сетевого отказа Docker Registry. Секрет подключения хранится вне репозитория, в отчёт не включён.

## Продолжение: OCR-обнаружение страниц без текста

Исправлен корень нулевого плана на скане: после текстовой карты страницы с изображением и <80 символами проходят существующий Docling/RapidOCR для поиска подписей таблиц. Никакие страницы или номера таблиц из D013 не передаются алгоритму. Принимаются только локализованные подписи `Table N` от детектора макета; произвольное упоминание таблицы в абзаце не превращается в целевой адрес. Вход и выход OCR, версии и настройки сохраняются вместе с SHA-256 PDF. OCR-кандидаты имеют `discovery=ocr` и идут сразу на OCR-чтение; подпись видна оператору как требующая сверки. Пустые/частично неудачные OCR-страницы не теряют предупреждения.

Контрольный тест полного D013 сначала упал: ожидалась Table 2/PDF 6, карта содержала 0 таблиц. После исправления прошёл за 174,79 с: подпись найдена по полному файлу, с координатами и исходным OCR-артефактом. Отдельный HTTP-тест подтвердил сохранение прямого OCR-плана без предварительной попытки TableFormer. Обработка цифрового D001 не переключается на OCR.

В среде обнаружился отдельный отказ: Torch-backend RapidOCR не смог скачать отсутствующий `PP-OCRv6_rec_small.pth` с ModelScope. Для приёмки использован поддерживаемый `onnxruntime` backend тех же RapidOCR с уже скачанными весами. Это явная настройка `RAG_OCR_BACKEND` на сервере/воркере; версия backend фиксируется в артефакте. Настройка не является выбором стратегии по названию файла. Для сравнения чисел после смены backend требуется самостоятельная сверка, улучшение точности по одному обнаружению не заявляется.

Чекер D013: структурных ошибок 0, exit 2, автоматически подтверждено 0/145 цитат: PDF является сканом, штатный native-text checker без OCR не подтверждает его текст. Это частичная публикация одной таблицы, не весь D013.

Третий прогон использовал два исполнителя параллельно с OCR всей карты. Подача файлов последовательная; пока строилась карта скана, отчёт ещё не опрашивал остальные карточки, поэтому `elapsed_seconds` — время до наблюдаемого завершения, верхняя граница. Перезапуск Hono был пережит с сохранением тех же прогонов. Значения третьего прогона не сравниваются как чистый benchmark скорости с первыми. Сумма длительностей попыток: D001 296,62 с, P003 113,31 с, mixed 204,61 с, D013 405,39 с. Для нового замера runner сохраняет отдельное время построения карты и timestamp публикации. Оптимизация повторного OCR одних страниц и изолированный замер времени остаются следующими действиями.

Регрессия runner: реальный локальный HTTP-сервер подтвердил подачу всех файлов и отсутствие новых POST при `--refresh`. Ошибка ранней версии refresh могла создать лишний непромеренный mixed-прогон; измеренный чекпойнт восстановлен по исходному run_id, лишний прогон не включён в сравнение. JSON/ZIP измеренных версий не менялись.

Для работы со сканом: установить `requirements-ocr-onnx.txt`, задать `RAG_OCR_BACKEND=onnxruntime` и Hono, и воркеру, затем повторить обычный вход полного PDF. Отдельные координаты/страницы в запрос не добавляются. По умолчанию поддерживается прежний Torch-backend, если его веса доступны. Естественный mixed PDF с таблицей-картинкой и произвольной цифровой подписью всё ещё требует отдельного контроля: текущий OCR-проход выбирает страницы без текста, а не каждую растровую область цифровой страницы.
