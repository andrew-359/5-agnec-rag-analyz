# Веб-автотесты Java для review-workspace

Срез от 22 ноября 2026 года. Первый набор стоит запускать на Java 21, Gradle Wrapper, JUnit 5, Selenium WebDriver и Allure. На каждый push проверяем реальный демоинтерфейс в Chrome с управляемыми HTTP-ответами. После этого добавляем один сквозной smoke на сохранённом D001 и короткие проверки реального API. Для выкладки отдельного демо требуется привязка к проверенному коммиту или образу. [План веб-интерфейса](../../.scratch/viniti-functional-acceptance/web-interface-plan.md#автотесты-на-java-и-cicd)

## Данные и запуск

- **Минимальный вариант.** Запускать рабочий `serve.py` из временной копии демо на выделенном loopback-порту. Сервер пишет в `assets/` рядом с собой и умеет проксировать два POST-маршрута сравнения. Достаточно локальной HTTP-фикстуры с проверкой метода, пути и идентификаторов запроса. Для ошибки страницы и восстановления можно использовать тестовый HTTP-прокси перед демо с переходом состояния после первого запроса. WireMock удобен, если понадобятся несколько маршрутов с независимыми состояниями, журналом запросов и явным сбросом между тестами. [Демосервер](https://github.com/andrew-359/RAG/blob/3c6c913e690aa1ba570cce8436b1f5d0ba6ede4b/web/prototypes/review-workspace/serve.py) · [Состояния WireMock](https://wiremock.org/docs/stateful-behaviour/)
- **Фикстуры.** Версионировать небольшие синтетические страницы, JSON и ZIP с известным содержимым. В режиме `export=local` согласовать контрольные строки с `d001.js` по ID, методу, числу, датасету, метрике, странице и таблице. Эти поля определяют, попадёт ли строка в демовыборку. Для отсутствующей версии вернуть `404`. Для повтора страницы выполнить последовательность `503 → 200` на одном адресе и сбросить состояние перед следующим тестом. Зафиксировать, какой запрос прошёл до и после клика «Повторить». [Загрузка публикации](https://github.com/andrew-359/RAG/blob/3c6c913e690aa1ba570cce8436b1f5d0ba6ede4b/web/prototypes/review-workspace/data.js) · [Выборка демо](https://github.com/andrew-359/RAG/blob/3c6c913e690aa1ba570cce8436b1f5d0ba6ede4b/web/prototypes/review-workspace/d001.js)
- **Сохранённый D001.** Явно закрепить `publicationId`, `versionId` и SHA-256 PDF из одного выпуска. Контроль из плана `version-f0821d2bc81ccd04145d39d751c8ebbf74fdf28f` использует R235 `.422` в Table 1 на PDF-стр. 6 и R253 `.422` в Table 2 на PDF-стр. 7. Брать ID из указанного выпуска. У `dev_gold` собственные ID. Для запуска с `--corpus` текущий `serve.py` ожидает также D009 и использует `pdftoppm`. Проверить входные файлы и доступность именно указанного выпуска до открытия браузера. В паспорте сверить предупреждение о частичном охвате, в исходном ZIP — манифест, паспорт, отчёт и состав семи CSV. [Контроли сравнения](../../.scratch/viniti-functional-acceptance/web-interface-plan.md#перенос-сравнения-на-демостенд) · [Запуск демо](https://github.com/andrew-359/RAG/blob/3c6c913e690aa1ba570cce8436b1f5d0ba6ede4b/web/prototypes/review-workspace/README.md) · [Аудит D001](article-audits/D001.md)
- **Изоляция.** Поднимать HTTP-процессы с ограниченным ожиданием готовности, сохранять их логи, завершать их при любом исходе. Для каждого теста создавать свою сессию браузера и каталог скачиваний. Фиксировать viewport, язык и часовой пояс, если от них зависят ожидания. Начать с последовательного запуска. Прогон из чистого checkout должен быть возможен с пустым кешем Gradle и без PDF из локальных `runs/`, ручного запуска стенда и секретов. [Изоляция тестов Selenium](https://www.selenium.dev/documentation/test_practices/encouraged/avoid_sharing_state/) · [Игнорирование локальных данных](../../.gitignore)

## Selenium, Gradle и Allure

- **Ожидания.** `WebDriverWait` может дождаться появления строки, загрузки изображения источника, исчезновения сообщения об ошибке после повтора и восстановления URL с нужным состоянием интерфейса. При перерисовке искать элемент заново. Смешивание implicit и explicit waits даёт непредсказуемые таймауты, `Thread.sleep` увеличивает задержку и оставляет гонку. Для действий подойдут доступные имена, а для строк и источников — устойчивые семантические локаторы с ID записи. Выносить в Page Object операции, которые повторяются. Бизнес-утверждения держать в тестах. [Ожидания Selenium](https://www.selenium.dev/documentation/webdriver/waits/) · [Page Object Models](https://www.selenium.dev/documentation/test_practices/encouraged/page_object_models/)
- **Браузер.** Установленный на runner Chrome подходит для первой пробы, но обновляется вместе с образом runner. Для проверки на каждый push предпочтительна полная версия Chrome for Testing и ChromeDriver из той же сборки. Передавать выбранный Chrome явно и писать обе версии в отчёт. Selenium Manager умеет управлять браузером и драйвером, при этом версия и источник бинарников должны быть явными. Один закреплённый Linux runner и Chrome headless дают достаточно данных, чтобы измерить длительность и решить, окупается ли матрица браузеров. [Chrome for Testing](https://developer.chrome.com/docs/automation-and-testing/chrome-for-testing) · [Совместимость ChromeDriver](https://developer.chrome.com/docs/chromedriver/downloads/version-selection) · [Selenium Manager](https://www.selenium.dev/documentation/selenium_manager/) · [Образы runner](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners#runner-images)
- **Скачивание.** Основной тест открывает паспорт в браузере, проверяет ссылку текущей версии и забирает её HTTP-клиентом. Когда стенд требует авторизации, передавать только нужные cookies тому же доверенному origin. Проверять статус и содержимое ZIP. Для одного сценария, который подтверждает именно клик «Скачать ZIP», настроить `download.default_directory` на абсолютный временный путь, дождаться полного файла с ограниченным таймаутом и открыть архив до `quit()`. Готовность скачивания в Chrome проверять явно. [Рекомендация Selenium](https://www.selenium.dev/documentation/test_practices/discouraged/file_downloads/) · [ChromeOptions](https://developer.chrome.com/docs/chromedriver/capabilities#set-download-directory)
- **Сборка.** Закрепить Java 21 через toolchain, версию Gradle через Wrapper, версии зависимостей и Allure. В `qa/java/` использовать `build.gradle.kts` и JUnit Platform. Предлагаемый вход для CI — `./gradlew check` с быстрым UI-набором. Живой E2E и REST Assured выделить в отдельные задачи `e2eTest` и `apiTest`. Сервер и браузер закрываются после теста независимо от результата. Проверять, что обязательная задача действительно выполнила тесты. [Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html) · [JUnit и интеграционные задачи в Gradle](https://docs.gradle.org/current/userguide/java_testing.html)
- **Диагностика.** Адаптер Allure пишет результаты, генератор собирает HTML. Закрепить совместимую пару версий с JUnit 5. Действующая справка указывает артефакт `allure-jupiter` вместо прежнего `allure-junit5`. Шаги называют действие и ожидаемый исход. При сбое прикладывать скриншот, URL, доступный браузерный лог, нужный фрагмент DOM и лог HTTP-фикстуры. Собирать до закрытия WebDriver, исходное исключение пробрасывать дальше. Для падения запуска Chrome сохранить логи процесса и версии, даже если скриншот невозможен. Для ошибки в подготовке или очистке учитывать отдельные callbacks JUnit. Не передавать в артефакты токены, cookies или закрытые PDF. [Адаптер Allure](https://allurereport.org/docs/junit-jupiter/) · [Вложения Selenium](https://allurereport.org/docs/guides/junit5-selenium-screenshots/) · [Обработка исключений JUnit](https://docs.junit.org/5.13.4/user-guide/#extensions-exception-handling)

## CI и выкладка

**CI на каждый push.** Проверять SHA события и записывать его с номером попытки workflow. Кешировать зависимости для ускорения. Собирать HTML Allure после успешного или упавшего тестового шага. Загружать HTML, `allure-results`, JUnit XML и журналы запуска даже при падении тестов или генератора. Шаги диагностики выполняются по условию статуса, исходный ненулевой код `./gradlew check` оставляет job красным. Сторонние Actions закреплять по полному commit SHA. [Событие push](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push) · [Условия статуса](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions) · [Артефакты](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts) · [Безопасность Actions](https://docs.github.com/en/actions/reference/security/secure-use)

**Отдельная выкладка из зелёного `main`.** Deploy job зависит от обязательного тестового job, допускает только push в `main` и использует выделенный ресурс демо. Отключить прямой auto-deploy по Git push для этого ресурса. Обычный запрос Coolify `/deploy` выбирает ресурс по UUID или тегу ресурса, а `docker_tag` в этом запросе относится к preview. Полномочия на вызов `/deploy` сами по себе не закрепляют ревизию. [Пример Coolify после CI](https://coolify.io/docs/applications/sources/github/actions) · [Параметры `/deploy`](https://coolify.io/docs/api/endpoints/deployments/deploy-by-tag-or-uuid)

Для ресурса review-workspace потребуется отдельная упаковка. Текущий `serve.py` слушает loopback, а Compose собирает штатный веб. Статическая сборка подходит для демо с комплектом фикстур. Если стенд должен показывать реальное сравнение, выбрать упаковку с прокси на действующий API и доступом к сохранённому выпуску. [Демосервер](https://github.com/andrew-359/RAG/blob/3c6c913e690aa1ba570cce8436b1f5d0ba6ede4b/web/prototypes/review-workspace/serve.py) · [Контекст сборки штатного веба](../../.dockerignore)

**Гонки и подтверждение.** Сериализовать операции изменения конфигурации и выкладки для одного ресурса. Перед изменением сверять, что workflow соответствует актуальной ревизии `main`, чтобы старые попытки не откатывали демо. Для двух быстрых push проверки выполняются для обоих SHA, а выпуск устаревшей ревизии можно пропустить по этому правилу. Сохранить UUID принятого deploy, дождаться конечного статуса и сверить наблюдаемую ревизию приложения. Штатный веб уже возвращает SHA из `/readyz`, статическому демо нужна метка сборки и проверка загрузки. При несоответствии завершать deploy job с ошибкой и сохранять SHA, digest при наличии, статус выкладки и результат smoke. Предыдущий рабочий SHA/digest нужен для повторяемого отката. **Доступ к стенду.** Hype отложен, в прежней схеме URL доступен через tailnet. Сначала принять CI на GitHub-hosted runner с синтетическими данными. Для выкладки и smoke закрытого демо выделить доверенный deploy-runner внутри tailnet или подключить отдельный hosted job к приватной сети. Хранить Bearer-токен Coolify в deploy environment, доступном `main`. Выдать `deploy` для запуска, `read` для опроса статуса и `write` только если job обновляет конфигурацию ресурса. Настроить отдельно права на push/pull образов и авторизацию на демо. ## Порядок приёмки

1. **Первый локальный срез.** Из чистого checkout проходят сценарий поиска ThreadRAG с открытием источника и восстановлением истории и сценарий ошибки PDF с успешным повтором. Намеренно вызвать падение проверки. В итоговом HTML есть исходная причина, скриншот, URL и журнал запроса. После восстановления ожидания оба теста зелёные.
2. **CI.** Повторить прогон того же SHA в чистом окружении и сравнить список выполненных тестов и статусы. Для намеренного падения сверить красный job и скачиваемые отчёты. После расширения набора зафиксировать длительность прогона и причины таймаутов. Один живой D001 smoke и REST Assured подключить отдельными командами, с явной ошибкой подготовки при недоступных данных.
3. **CD.** После согласования отдельного ресурса и доступа показать, что красный `main` сохраняет прежний выпуск, зелёный публикует свой SHA или digest, а повтор старого workflow не меняет стенд. Сохранить ссылку на GitHub Actions, отчёт тестов и UUID и результат выкладки. Состояние демо подтвердить запросом к работающему приложению.
